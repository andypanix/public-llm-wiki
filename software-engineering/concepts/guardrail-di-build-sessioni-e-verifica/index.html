Guardrail di Build, Sessioni Parallele e Verifica

Nell'SDLC nativo IA descritto dal playbook di Anthropic (Louis Claxton, agosto 2026), l'autonomia di Claude Code durante le fasi di sviluppo e di test poggia su una stratificazione precisa dell'harness: file CLAUDE.md e Skills forniscono il contesto e i controlli consultivi, gli hook applicano i vincoli deterministici, i git worktree e i subagenti moltiplicano la capacità di esecuzione e i cicli di feedback insieme alle eval continue in CI verificano che né il codice né la configurazione dell'agente degradino nel tempo. 1

CLAUDE.md: il contesto del primo giorno in una pagina

Il file CLAUDE.md raccoglie il contesto che servirebbe a un nuovo membro del team nel suo primo giorno di lavoro: comandi di build e test, convenzioni di codice, architettura del servizio ed errori ricorrenti (vedi anche Context Engineering). 1 Conoscenze che in precedenza restavano sparse nella memoria delle persone o in wiki separate diventano un file nella radice del repository Git, letto da Claude all'inizio di ogni sessione e rivisto nelle pull request con l'approvazione dei code owner.

Il playbook raccomanda cinque passaggi operativi per gestirlo:

  1. Generare una prima bozza eseguendo /init nel repository, lasciando che Claude ispezioni la codebase.
  2. Potare il file generato tenendo solo ciò che è indispensabile il primo giorno: comandi di build, test e lint, convenzioni non ovvie e punti su cui l'agente sbaglia.
  3. Mettere CLAUDE.md sotto controllo di versione nella radice del repository, così che tutto il team condivida la stessa versione.
  4. Applicare la regola del secondo errore: ogni volta che Claude commette lo stesso errore due volte, la correzione entra in CLAUDE.md.
  5. Mantenere il file entro una pagina, perché Claude lo carica per intero a ogni avvio di sessione e qualsiasi riga obsoleta consuma finestra di contesto senza dare alcun beneficio (vedi Cerimonia Proporzionata al Rischio).

Nell'esempio del playbook per un servizio di pagamenti (Payments service), CLAUDE.md elenca i comandi make build, make test (unit test), make itest (test di integrazione con Docker) e make lint; fissa le convenzioni su Java 21 e Spring Boot 3 (niente nuovo Lombok, una libreria Java di generazione di codice tramite annotazioni 2; importi monetari sempre in BigDecimal e mai in double; test di integrazione obbligatorio in src/itest per ogni endpoint); riassume l'architettura (api/ per i controller REST, core/ per la logica di dominio, adapters/ per i sistemi esterni e schemas/ per gli eventi Kafka, un sistema di event streaming distribuito, specificando di non modificare mai le classi generate) e chiude con la sezione Things Claude gets wrong: non aggiornare le versioni delle dipendenze (gestite dal team di piattaforma) e non toccare il pacchetto legacy v1/ congelato, inserendo le modifiche in v2/.

Le Skills come conoscenza istituzionale e il confine tra consultivo e deterministico

Se CLAUDE.md descrive il singolo repository, le Skills sono lo strumento con cui l'organizzazione rende operativa la propria conoscenza istituzionale trasversale, come uno standard di sicurezza, una convenzione di design delle API o una regola di brand. 1 La regola pratica di Claxton è scrivere una Skill per le regole aziendali che devono essere applicate in modo uniforme su più attività, evitando invece di usarla per istruzioni che appartengono a CLAUDE.md o a un singolo prompt.

Una Skill è una cartella (salvata nel repository sotto .claude/skills/<name>/ o distribuita a tutta l'organizzazione tramite un plugin) che contiene un file SKILL.md: il frontmatter YAML (name e description) definisce quando la Skill deve attivarsi, mentre il corpo elenca i passi da eseguire. Uno sviluppatore la redige con l'aiuto di Claude a partire dalla fonte di verità del responsabile della policy (policy owner), verifica che si carichi regolarmente provando a formulare la richiesta in modi diversi e, quando la policy cambia, fa approvare l'aggiornamento al policy owner così che tutti i team ricevano la nuova versione nella sessione seguente.

L'esempio mostrato dal playbook è .claude/skills/secure-api-review/SKILL.md, che si attiva a ogni creazione, modifica o revisione di un endpoint esterno o di una specifica OpenAPI (lo standard per descrivere API HTTP 2) e impone quattro controlli più l'esecuzione dello script scripts/check-endpoints.sh:

  • Autenticazione: ogni endpoint richiede il JWT (JSON Web Token, un formato di token di autenticazione firmato 2) del gateway, senza rotte anonime al di fuori di /health.
  • Validazione dell'input: i corpi delle richieste vanno validati contro lo schema OpenAPI rifiutando i campi sconosciuti.
  • Audit: ogni endpoint che modifica lo stato deve emettere un evento di audit con attore, azione, entità e timestamp.
  • Classificazione dei dati: i campi marcati pii nello schema non devono mai comparire nei log o nei messaggi di errore.

Sul piano della governance il playbook traccia una distinzione fondamentale tra controllo consultivo e controllo deterministico. Una Skill è un controllo consultivo: rende molto probabile che Claude segua la policy mentre scrive il codice e registra l'invocazione nelle tracce di sessione, ma nulla impedisce tecnicamente al modello di discostarsene. Quando una policy non ammette eccezioni, la Skill va affiancata a un meccanismo deterministico, cioè un hook che blocca l'azione o un controllo nella pipeline di pull request: nella formulazione di Claxton, la Skill rende le violazioni rare, mentre l'hook le rende quasi impossibili.

Gli hook come barriere deterministiche in fase di build

Gli hook sono script deterministici eseguiti automaticamente dall'harness in corrispondenza delle azioni dell'agente. Poiché durante l'implementazione Claude opera soprattutto modificando file e lanciando comandi di shell, la fase di build è quella in cui gli hook scattano più di frequente. 1

In questa fase gli hook vengono usati per tre scopi principali:

  • bloccare le modifiche a percorsi protetti, come le classi generate dagli schemi o un pacchetto legacy congelato;
  • eseguire formatter e linter subito dopo la modifica di un file, evitando che le incoerenze di stile si accumulino;
  • impedire che credenziali o segreti finiscano nel diff.

Poiché un hook di build gira a ogni azione corrispondente dell'agente, deve essere rapido e circoscritto al singolo file appena toccato; le verifiche pesanti, come l'esecuzione dell'intera suite di test, vanno invece spostate al momento del commit o della pull request. Allo stesso modo, Claxton avverte di non inserire in fase di build hook che chiedono un'approvazione umana interattiva: vanno riservati ai gate di distribuzione (vedi Review, Rilascio e Chiusura Autonoma del Ciclo), altrimenti un prompt di conferma rimetterebbe una persona nel percorso critico di tutte le sessioni che stanno lavorando in parallelo.

Sessioni parallele nei git worktree e subagenti

Con i guardrail attivi un singolo sviluppatore può coordinare più flussi di lavoro contemporaneamente combinando due strumenti distinti: le sessioni parallele e i subagenti (per l'esperienza su flotte ancora più ampie si veda Flotta di Agenti). 1

Una sessione parallela è un'istanza completa e indipendente di Claude Code che lavora su un'attività separata dentro il proprio git worktree, cioè una copia locale distinta del repository legata a un proprio branch (avviata per esempio con claude --worktree feature-auth in un terminale e claude --worktree fix-rate-limit in un altro). Le sessioni non sanno l'una dell'esistenza dell'altra e grazie ai worktree non entrano in conflitto sui file: lo sviluppatore usa il plan.md per individuare i task che toccano file disgiunti, mentre tiene in un'unica sessione sequenziale le attività che condividono gli stessi file. Secondo il playbook due o tre sessioni parallele sono un buon punto di partenza, perché il vero limite non è la macchina ma il numero di flussi che una persona riesce a revisionare con attenzione.

Un subagente vive invece dentro una singola sessione come assistente specializzato: ha una propria finestra di contesto separata e un elenco ristretto di strumenti accessibili, così da svolgere compiti ricorrenti senza inquinare il contesto dell'agente principale. I subagenti si definiscono in file markdown versionati sotto .claude/agents/ e condivisi da tutto il team; il playbook ne cita tre esempi:

  • un code simplifier, che ripulisce le complessità superflue una volta che l'agente principale ha terminato;
  • un researcher, che esplora la codebase e restituisce solo le conclusioni senza riempire la finestra di contesto principale;
  • un verifier (.claude/agents/verifier.md), limitato ai soli tool Bash e Read, a cui viene chiesto di avviare l'applicazione con make run, mettere alla prova il comportamento modificato e i due flussi adiacenti più vicini e riferire che cosa ha eseguito e qualsiasi scostamento da plan.md, con il divieto esplicito di correggere alcunché ("Do not fix anything; report only").

Poiché più sessioni moltiplicano l'output, la governance deve poggiare sulla configurazione del repository: hook e permessi definiti nel progetto valgono per tutte le sessioni e ogni azione resta registrata e attribuita allo sviluppatore che ha lanciato la sessione.

Ciclo di feedback dell'agente e protezione dei test

Il playbook insiste sulla differenza tra il ciclo di feedback e il subagente verificatore. Il ciclo di feedback accompagna l'intera attività e viene ripetuto dall'agente principale tutte le volte necessarie per correggere i propri errori prima ancora che uno sviluppatore guardi il codice; il subagente verificatore interviene invece una sola volta alla fine, dentro una finestra di contesto vergine, così che il controllo finale non sia condizionato dalle ipotesi che hanno guidato la scrittura del codice (vedi anche Lifecycle delle Skill di Osmani e Elephant-Goldfish Model). 1

Per dare a Claude un ciclo di feedback efficace, Claxton indica sette pratiche:

  1. Racchiudere sequenze complesse di verifica in un unico comando target (come make test o npm test) che restituisca un codice di uscita diverso da zero in caso di fallimento.
  2. Elencare ogni comando nella sezione Commands di CLAUDE.md insieme alla stringa che identifica l'esito positivo (per esempio make build deve terminare con "Build succeeded").
  3. Dare obiettivi quantificabili e verificabili senza domande all'umano, come "tutti i test in test_status.py passano", "lo screenshot corrisponde al mockup allegato" o "l'endpoint restituisce 200 col nuovo campo".
  4. Per i bug fix, imporre il test-driven development: chiedere prima a Claude di riprodurre il bug con un test, verificare che fallisca per il motivo atteso ed eseguire il commit del test; solo dopo chiedere la correzione del codice, vietando modifiche al test.
  5. Per le interfacce utente, chiudere il ciclo con una verifica visiva fornendo a Claude un browser o uno strumento di screenshot insieme al mockup: in media bastano due o tre cicli di implementazione, cattura dello screenshot, confronto e ritocco.
  6. Inserire la verifica nella definizione di "completato" dentro CLAUDE.md (sezione Verifying your work), obbligando l'agente a eseguire build, test e lint con zero warning e a incollarne l'output prima di dichiarare concluso il task.
  7. Proteggere il ciclo di verifica stesso con la regola "If a test fails, fix the code, not the test": un hook che blocca la modifica dei file di test durante un'attività di fix (o il rifiuto in sede di code review di qualunque diff che tocchi il test preesistente) impedisce all'agente di superare l'ostacolo indebolendo o cancellando il controllo (vedi anche Competenze del Developer nell'Era AI).

Eval continue nella CI come test di regressione dell'harness

Nella fase di test le eval rappresentano l'equivalente nativo IA dei gate di controllo qualità tradizionali: sono una suite di valutazione che verifica se l'agente continua a lavorare allo stesso livello qualitativo ogni volta che cambia la sua configurazione (un nuovo modello, una riscrittura di CLAUDE.md, una modifica alle Skills o agli hook). 1

Per costruirla, un ingegnere del team di piattaforma raccoglie da 20 a 50 attività reali tratte dal lavoro recente, ciascuna con il proprio risultato atteso o accettato, e le codifica come file di eval (.json) che accoppiano il prompt ai controlli di accettazione eseguiti da uno script (./evals/check.sh: superamento dei test, assenza di errori di lint, comportamento preservato, rispetto delle policy).

Nell'esempio di workflow GitHub Actions (.github/workflows/agent-evals.yml), la suite gira in modalità non interattiva (claude -p con --allowedTools "Read,Edit,Bash(make test)" --output-format json) sia a cadenza giornaliera programmata (cron: '0 2 * * *') sia a ogni pull request che tocca CLAUDE.md o .claude/**, trattando la configurazione che guida l'agente con gli stessi test di regressione riservati al codice applicativo. Se una modifica a una Skill abbassa il tasso di superamento delle eval, il merge viene bloccato o sottoposto a revisione.

Claxton sottolinea che una suite di eval non è mai statica: man mano che i modelli migliorano, i casi che un tempo distinguevano una buona configurazione da una cattiva smettono di discriminare e vanno sostituiti con casi nuovi provenienti dal monitoraggio continuo. Inoltre, ogni incidente di produzione genera una nuova eval scritta dal team responsabile del servizio colpito, che resta nella suite come test di regressione permanente.
